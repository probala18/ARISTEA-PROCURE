# Module 18 — Deployment & Production Readiness

## Objective

Module 18 makes the existing application reproducibly installable, explicitly
configurable, and locally verifiable in a production-like ASGI process without
changing BIS/procurement intelligence or Module 16 evaluation behavior.

## Deployment baseline

The pre-change audit is recorded in
[module18-deployment-baseline.md](./module18-deployment-baseline.md).
The repository already had FastAPI health/readiness routes, Alembic metadata,
environment-backed settings, bounded job lifecycle cleanup, and Module 17
security controls. It did not have a dependency manifest, container definition,
deployment guide, or useful README.

## Runtime and installation

- Tested Python runtime: **3.13.10**.
- Dependency strategy: [requirements.txt](../requirements.txt).
- Setup: create a Python 3.13 virtual environment, install the requirements,
  and copy [.env.example](../.env.example) to `.env`.
- Application command:
  `uvicorn backend.app.main:app --host 0.0.0.0 --port 8000`.

The dependency manifest describes runtime packages used by the existing
FastAPI, SQLAlchemy, Alembic, PostgreSQL/pgvector, parsing, retrieval, and
speech integrations. It does not add a new domain dependency or data source.

## Environment configuration

The example file contains placeholders only. Important variables include
`DATABASE_URL`, PostgreSQL connection fields, `ENVIRONMENT`, `LOG_LEVEL`,
`CORS_ALLOWED_ORIGINS`, `MAX_UPLOAD_BYTES`, `MAX_AUDIO_BYTES`,
`MAX_EVALUATION_QUERIES`, and `DATA_DIR`.

Module 17 controls remain active: upload limits, safe filenames, content-type
checks, dataset path restrictions, generic external errors, security headers,
and configurable CORS.

## Database and ingestion

Operational order:

1. Configure `.env`.
2. Create the target database.
3. Run `alembic upgrade head`.
4. Run `python -m scripts.ingest --data-dir csvfiles`.
5. Run `python scripts/validate_ingestion.py`.
6. Start the API.

Alembic now reads `DATABASE_URL` from application settings. Application startup
does not run migrations or ingestion and does not modify domain data.

## Containerization

A minimal [Dockerfile](../Dockerfile) uses Python 3.13, installs the declared
requirements, copies application code and supplied data, exposes port 8000,
and starts Uvicorn. It contains no credentials. Database setup, migration, and
ingestion remain explicit steps and are not hidden in the image command.
The image health check calls the existing read-only `/api/health` endpoint.
Kubernetes, compose, cloud infrastructure, and distributed services remain
out of scope.

## Health and readiness

- `GET /api/health` is a liveness response and does not query the database.
- `GET /api/ready` performs the existing read-only `SELECT 1` check.
- `/openapi.json` and `/docs` are generated by FastAPI.

## Storage and lifecycle

- Canonical BIS/procurement data is stored in the configured database.
- Supplied source files remain external input data and are not rewritten by
  application startup.
- Tender/audio request bodies are processed in memory by the existing services.
- TTS temporary files are temporary and provider-managed.
- Asynchronous job records remain process-local and in memory.
- Generated specifications are persisted through the existing database model.
- Evaluation observations are persisted through the existing evaluation tables.

No indefinite document archive or object storage was added.

## Logging

`LOG_LEVEL` controls the application logger. Unexpected exceptions are logged
internally while external responses remain generic. The deployment
configuration does not log credentials, tokens, database URLs, tender bodies,
or raw audio.

## Verification

- Module 18 focused tests: **3 passed, 0 failed**.
- Full cumulative regression: **196 passed, 0 failed, 463 warnings**.
- Ingestion validation: **passed**.
- Dataset counts remained 268 standards, 111 relationships, 275 versions,
  710 QCO records, 1,573 certification records, 75 product licences,
  28 ministry mappings, and 14 evaluation queries.
- Core provenance coverage remained **100%**.
- Module 16 benchmark methodology and recorded results remain unchanged.

The deployment surface was verified through TestClient for health, OpenAPI, and
security headers. A full PostgreSQL/container run depends on the environment's
Docker daemon and database availability; no unsupported production claim is
made.

## Limitations and future deployment work

This module does not add authentication, authorization, distributed queues,
autoscaling, external monitoring, WAF, cloud deployment, multi-region support,
or formal security certification. Job state remains process-local, and
database migrations/ingestion remain explicit operator actions.
